## 1. 产品摘要

《英语商业街》是一款面向“学过一些英语、但在真实生活中用不出来”的成年初级英语学习者的第一人称 3D 情境经营模拟游戏。

玩家从经营一家英国街区小便利店开始，以人的视线高度自由走动、搬运货箱、观察商品并上架；顾客自主浏览、拿取商品并走到收银台，玩家完成扫码和收款。英语通过认识实物、读送货单、回答位置、确认数量和付款要求融入经营，不让每次搬运都变成一道弹窗题。

为了与“去英国当顾客”的真实需求对齐，玩家也会在进货、探店和日常采购任务中切换为买方，主动询价、找商品、确认数量和点单。营业所得可直接购买普通货架、容量和基础扩容；高级服务与自动化另需完成对应英语任务。自动化不会消灭英语学习，而会把任务从重复交易升级为培训、检查和处理简单异常。

毕业版首先验证一件事：

> 当英语与可辨认的实物、经营操作和高级服务责任相联系时，玩家是否愿意主动、反复地调用英语，并能否把所学迁移到没有原样见过的新菜单、新商品和新说法中。

## 2. 背景与问题

### 2.1 用户问题

目标学习者并非完全没有接触过英语。他们可能长期观看英语直播、短视频或课程，认识一些单词，也能理解简单句子，但真实场景出现时仍会遇到以下困难：

- 在餐厅看不懂菜单，不知道一道食物究竟是什么；
- 在超市不知道想买的食品或生活用品用英语怎么说；
- 听不清服务人员说出的商品、数量、价格或特殊要求；
- 知道单词，却无法及时组织成得体、能完成任务的句子；
- 没听懂时不知道如何请对方重复、确认或修正误会；
- 真实交流机会少、犯错压力高，学习内容长期停留在“看过”而不是“会用”。

### 2.2 现有方式的缺口

直播、短视频、背词和跟读主要提供输入或模仿，但通常缺少：

- 一个必须使用英语才能完成的明确目标；
- 可反复尝试、失败成本低的真实任务；
- 同一意图在不同说法和新情境中的迁移练习；
- 能支持长期回访的成长、装修、赚钱和扩张动力。

### 2.3 产品机会

经营模拟天然包含商品、价格、顾客、订单、服务和突发情况，可以把生活英语放进有因果关系的任务中。英语不是经营之外弹出的测验，而是玩家经营店铺的工具。

欧洲委员会 CEFR 的 A2 “获取商品与服务”能力描述包含日常饮食和购物、价格与数量、简单购买、点餐和指出简单问题，与本产品的核心场景高度匹配。因此第一座城市以英式英语生活交易为内容基线，面向大致 A1–A2 的学习者，选取其中部分交易能力进行练习。本项目不以短期训练使学习者“整体达到 A2”为目标。[CEFR Companion Volume（第 77 页）](https://rm.coe.int/cefr-companion-volume-with-new-descriptors-2020/16809ea0d4)

## 3. 产品定位

### 3.1 一句话定位

> 一款让成年初级学习者通过经营英国商业街，把“学过的英语”转化为“生活中能用的英语”的情境经营模拟游戏。

### 3.2 核心价值主张

- 对学习者：在低压力的模拟世界中反复完成购物和服务任务，逐渐敢用、会用英语。
- 对玩家：通过赚钱、装修、雇员和自动化获得持续成长，而不是连续做孤立练习题。
- 对毕业研究：形成可记录、可对照、可迁移测试的学习行为和任务表现数据。

### 3.3 产品设计支柱

1. **英语推动经营**：英语任务的结果必须影响订单、满意度、收入或升级进度。
2. **经营产生新语言需求**：店铺升级后出现新的角色、异常和管理任务，而非简单减少学习量。
3. **先少量接触，再立即使用**：通过近看商品、送货单和简短提示认识当天必要内容，随后在真实操作与顾客情境中调用，不要求先上完一节独立词卡课。
4. **低压力失败**：失败影响当天收入和评价，不造成永久破产或大段进度丢失。
5. **短时可玩，长期成长**：单次游戏可在碎片时间完成，长期仍有扩张和装修目标。
6. **成年人友好**：画面、文案和角色比例不幼稚；操作与辅助适合低游戏经验用户。
7. **买卖双角色**：核心学习单元同时包含玩家作为买方主动表达和作为卖方理解/回应的任务，不用店员成绩代替顾客能力。
8. **实物可辨认、成长分层**：教学商品通过形状、材质和场景用途建立词义联系；普通经营扩容不被英语门槛阻挡，高级能力要求对应的语言责任。

## 4. 目标与非目标

### 4.1 毕业版 V1 产品目标

| 编号 | 目标 | 验证方式 |
| --- | --- | --- |
| G-01 | 做出“拿箱/认识商品 → 上架 → 顾客自主购物 → 收款 → 成长 → 新英语任务”的第一人称闭环 | 端到端试玩与验收测试 |
| G-02 | 区分普通经营成长与高级能力的解锁条件 | 普通升级资金足够即允许购买；高级服务/自动化需资金与对应英语任务，玩家能解释两类条件 |
| G-03 | 支持大学生完成可用性、可行性与模拟情境近迁移的初步研究，并单独探索中年成年人的桌面可用性 | 前测、后测、延迟测试、可用性访谈 |
| G-04 | 在常见 Windows 与 macOS 桌面浏览器中稳定运行 | 自动化跨浏览器测试 + 真实设备人工测试 |
| G-05 | 形成可解释、可维护、可在答辩中说明的代码与内容结构 | 模块说明、测试、版本记录、演示 |

### 4.2 学习目标

玩家经过首发内容后，应能在新的生活交易任务中更好地：

- 识别常见食品、饮品和生活用品名称；
- 提取商品、数量、价格、口味、位置和特殊要求；
- 使用简单、得体的句块完成询问、推荐、确认和结账；
- 在没有听懂或信息冲突时请求重复、澄清和确认；
- 将已经练过的意图应用到未原样出现的新商品与新表达中。

上述目标分别从买方与卖方角色测量。V1 的实物指认、操作、选择和词块任务主要测量词义辨认、听读理解、语用选择和受支架表达，不把它等同于自由口语流利度；3D 美术提升记忆的效果仍需验证。

### 4.3 非目标

毕业版 V1 不承诺：

- 系统教授完整语法体系或覆盖考试英语；
- 训练母语者口音或以口音相似度作为主要成绩；
- 使用开放式大模型生成所有顾客对话；
- 实现多人联机、玩家交易或社交社区；
- 实现电影级角色、任意物理堆叠、破坏系统或完整人体物理；
- 同时发布 Windows、macOS、iOS、Android 原生安装包；
- 完整实现四类店铺的同等深度“商业帝国”；
- 通过一次小规模实验证明产品对所有年龄人群都有效。
- 证明学习者的整体 CEFR 等级发生提升；
- 证明玩家已具备真实英国环境中的自由口语交流能力。

## 5. 用户与研究对象

### 5.1 主目标用户：毕业版正式验证对象

**18–25 岁、非英语专业大学生，生活英语大致处于 A1–A2。**

典型特征：

- 接受过多年英语教育，能认出部分词汇和简单句型；
- 面对英文菜单、购物或口头服务情境时仍会犹豫；
- 缺少真实、可重复的使用环境；
- 能接受经营、升级、装修和收集等游戏机制；
- 便于持续招募、测试和完成毕业论文研究。

### 5.2 次目标用户：探索性验证对象

**40–60 岁、近期主动学习英语但缺少使用机会的成年人。**

典型特征：

- 通过直播、短视频、课程学习单词、语法或日常对话；
- 认识一些单词，可理解非常简单的句子；
- 游戏经验可能较少，对第一人称移动与视角操作的接受度需要单独验证，不能由英语基础推断；
- 学习动机可能是旅行、探亲、工作实用或个人兴趣；
- 更需要清晰引导、较大文字、慢速语音和可重复播放。

毕业论文中，成年人数据用于需求和可用性探索，不与大学生样本合并后宣称普遍学习效果。

### 5.3 内容与研究协作者

英语教师不是主要玩家，而是：

- 审核词汇、句型、语用是否自然；
- 判断 A1–A2 难度和提示梯度；
- 审阅平行测试题，避免只测原句记忆；
- 协助界定何为“完成真实任务”。

### 5.4 核心用户任务（JTBD）

- 当我将来需要在英国购物或点餐时，我希望提前在不尴尬的环境中练习，这样真实交流时能完成任务。
- 当我已经看过一些英语内容却总是记不牢时，我希望立刻把它用于有结果的行动，这样能从“认识”变成“会用”。
- 当我只有十分钟空闲时，我希望完成一个营业日并得到可见成长，而不是开始一节无法结束的长课。
- 当我不会玩复杂游戏时，我希望系统一步一步告诉我该做什么，但不把我当小孩子。

## 6. 学习设计

### 6.1 内容边界

- 首座城市：英国商业街，优先使用英式英语表达、拼写、货币和生活语境。
- 能力范围：面向大致 A1–A2 的学习者，对齐 CEFR 中“获取商品与服务”“目标导向合作”和“请求澄清”的部分描述；自制校准不构成 CEFR 认证。
- 核心技能：场景词汇、标签/菜单阅读、交易听力、词块表达、沟通修复。
- 非核心技能：长篇写作、学术阅读、系统语法讲授、口音打分。
- 问题范围：V1 只处理可用简单表达解决的问题，例如拿错商品、食物冷了、扫码或付款失败；正式投诉、协商赔偿和复杂争议作为 B1/V2 以后内容。
- 结果边界：V1 只验证选定模拟交易任务中的表现，不声称学习者整体达到 A2。

### 6.2 单次学习闭环

单个营业日采用以下结构：

| 阶段 | 预计时间（待验证） | 玩家行为 | 学习作用 |
| --- | ---: | --- | --- |
| 今日准备 | 1–2 分钟 | 在检查货箱、近看商品或送货单中接触 3–6 个必要词/词块，并完成一次买方采购任务 | 连接词义与实物，降低首次任务负荷并练主动需求表达 |
| 营业实践 | 5–7 分钟 | 上架并服务自主购物的顾客，在询问和结账时完成不同说法的卖方任务 | 在目标驱动中理解、回应和修复，而非代替每位顾客取货 |
| 当日复盘 | 约 1 分钟 | 查看错误、重听关键句、选择明日重点 | 巩固并形成下一次复习计划 |

普通营业日目标仍为 8–10 分钟；装修和复杂升级位于营业日之间，不计入该时长。首次会话因包含第一人称操作教程和校准，原 12–15 分钟估计需在 3D 小样后复核。开场约五分钟的小循环见 7.8；它不是整个首日，也不是强制倒计时。所有时长都是待验证假设。

### 6.3 输入难度阶梯

同一沟通意图应随游戏内技能进度逐步减少支架：

1. **识别**：根据词语或需求观察、指出或拿取对应实物；涉及表达时可从 2–4 个回答中选择；
2. **组织**：拖拽或点击词块组成句子；
3. **主动表达**：键入关键内容，或在支持设备上自愿使用语音；
4. **迁移**：换商品、换顾客、换说法后完成同一意图。

自由语音不是首发必经路径。浏览器 `SpeechRecognition` 尚不能在所有主流浏览器中稳定使用，部分实现还依赖服务器，因此只可作为渐进增强，不能阻挡核心流程。[MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)

### 6.4 学习支援模式

进入游戏时不只提供“有基础/无基础”二选一。初始目标是玩家在 60 秒内完成第一个受引导的有效操作，例如拿起货箱或近看一件商品，而不是必须先接待顾客。英语校准嵌入教程和首日任务，不单独阻塞开店；校准累计用时暂定不超过 3–5 分钟，再推荐模式。玩家可以跳过或随时修改。

| 模式 | 适合人群 | 字幕与中文 | 操作形式 | 语音 |
| --- | --- | --- | --- | --- |
| 引导模式 | 零基础或低游戏经验 | 中英对照，关键词高亮 | 实物操作引导 + 选择，允许多次重听 | 慢速优先 |
| 实用模式 | A1–A2 学习者 | 英文为主，中文按需显示 | 实物操作 + 选择/词块拼接 | 正常速度，可降速 |
| 沉浸模式 | 希望增加挑战者 | 默认英文，中文按需或错误后提示 | 实物操作 + 词块，键入或语音按对应版本开放 | 正常速度 |

“游戏操作教程”和“英语支援强度”分别设置，避免英语基础好但不会玩游戏的人被错误分组。

### 6.5 反馈原则

- 第一次错误：让顾客用更简单的说法重述或指出矛盾；
- 第二次错误：高亮订单中的关键信息；
- 第三次错误：给出可直接使用的答案并允许立即重做；
- 反馈解释“为什么不合适”，避免只显示红叉；
- 对能够完成任务的不同礼貌表达予以接受，不强制唯一答案；
- 错误影响本次服务效率或满意度，但不羞辱玩家、不终止当天营业。

### 6.6 游戏内技能进度估计

每个学习点记录四个状态：

1. 已接触；
2. 在提示下成功；
3. 独立成功；
4. 在变式任务中迁移成功。

“独立成功”指首次作答、未使用提示且答案满足关键任务条件；反复试错后通过不得记为独立成功。普通货架、容量和基础扩容不读取此门槛。高级服务与自动化按各自的前置英语任务清单判断，不只看“做题次数”或所有技能的总数。建议的首轮资格规则是：对应任务的关键技能出现独立成功，并至少在一个相关变式任务中成功，再与经营资金共同满足解锁条件；具体任务和阈值待内容审核及试玩后冻结。每个技能都应提供不消耗经营资源的补练路径，条件能否在 2–3 个正常营业日内达到仍待验证。

该状态只用于调整游戏支架与控制进度，不代表真实“掌握”，也不作为正式学习效果指标。正式指标来自独立的前测、后测和延迟测试。

### 6.7 各店铺语言内容路线

| 店铺阶段 | 主要词汇 | 核心交流任务 | 新的沟通修复 |
| --- | --- | --- | --- |
| 小便利店 | 食品、饮料、日用品、数字、价格 | 找商品、询价、数量、袋子、收据、付款 | 请重复、确认数量和价格 |
| 大型商超 | 货架区域、重量、促销、替代品 | 指路、称重、缺货替换、自助结账 | 支付失败、扫码错误、商品不符 |
| 饮品店 | 杯型、冷热、甜度、奶类、加料 | 推荐、定制饮品、确认订单 | 漏项、错杯、过敏信息 |
| 餐厅 | 菜单、配料、烹饪、套餐、账单 | 点餐、修改、推荐、结账 | 忌口、过敏、指出简单问题 |

### 6.8 买卖双角色与近迁移

每个 P0 核心学习单元至少包含：

- 一次买方任务：玩家通过进货、探店或生活采购，主动找商品、询价、说明数量、确认替代品；
- 一次卖方任务：玩家在营业中听取顾客需求，回答位置、确认订单并完成交易；
- 一次变式：更换商品、数量、说话人、句式或界面版式。

买方短任务复用同一套对话、订单和判定系统，可使用轻量静态场景或采购界面，不新增另一套完整经营模拟。P0 至少包含 4 个此类任务，其中可用饮品店或餐厅作为短场景，但这不等于实现完整饮品店或餐厅经营线。

V1 所称“迁移”只指模拟情境中的近迁移：

| 层级 | 定义 | 是否可用于研究结论 |
| --- | --- | --- |
| T1 | 相同意图，更换商品或数量 | 可报告项目变式表现 |
| T2 | 相同意图，更换句式、说话人或菜单/标签版式 | 正式测试至少覆盖此层 |
| T3 | 相同能力切换买卖角色或应用到另一类店铺 | 只有实际测试后才讨论跨场景近迁移 |

前测和后测采用 A/B 平行任务并交换施测顺序，由教师审核难度和答案范围。不得把 T1–T3 表述为已经证明真实英国交流能力。

### 6.9 学习单元内容规范

每个可发布学习单元必须记录：CEFR 对应描述、买方/卖方角色、输入技能、输出技能、正确表达、可接受变体、干扰项理由、提示、音频、复习项、研究保留项和教师审核状态。

### 6.10 实物词义联系与提示边界

- 每个教学商品有稳定的商品 ID，并关联英文、中文释义、计量单位、发音、3D 模型、材质和合法陈列位置；例如 milk 对应牛奶，a carton of milk 对应一盒牛奶。
- 同一商品在货箱、手中、货架、顾客购物篮和收银台保持相同身份与外观，不能在近看时换成另一种包装。
- 玩家主动近看时展示简短词义和发音入口；放下后继续操作，不强制背完词卡或每次重复答题。
- 从“有词义辅助地看商品”逐步过渡到“根据英文找出/指出实物”；仅看过标签只能记为接触，不等于独立成功。
- 普通交互轮廓表示“这里可以操作”；独立辨认任务不能只让正确商品发光、提前显示中文答案或用独有颜色泄漏答案。
- 教学提示可按需开启，使用后如实记录提示级别；操作教程与语言提示分开记录。
- 变式应包含不同商品、位置、数量、说法或经过审核的新包装，避免只学会固定位置和颜色。正式测试仍遵守研究保留项规则。

## 7. 游戏设计

### 7.1 世界与成长幻想

玩家以几乎一无所有的状态接手英国街区的一家小便利店。初期所有关键工作需要亲自完成；随着经营与英语能力成长，玩家扩建店面、招聘员工、引入设备，并最终管理一条包含零售和餐饮业务的商业街。

长期产品路线分为两条业务线：

- 零售线：小便利店 → 社区超市 → 大型商超；
- 餐饮线：饮品店 → 咖啡/轻餐 → 餐厅。

当零售线进入自动化后，玩家投资第一家小饮品店，再次回到亲手服务阶段。这样既保留“从手工到自动化”的满足感，也避免后期完全失去英语互动。

### 7.2 核心循环

```text
查看今日目标、送货单并认识少量实物
        ↓
进货 → 搬箱 → 近看商品 → 上架
        ↓
顾客自主浏览、拿货并前往收银台
        ↓
回答英语询问、扫码与收款
        ↓
获得收入、评价和游戏内技能进度
        ↓
复盘；用钱购买普通扩容，完成对应英语任务后解锁高级能力
        ↓
出现新顾客、新异常与新店铺
```

### 7.3 单日流程

1. **准备阶段**：查看今日重点，以买方身份完成一次进货/采购任务，搬运和打开货箱、认识商品并上架。
2. **营业阶段**：顾客自主进入、浏览、拿货、按需询问并排队结账；玩家补货、指路、处理需求和收款，不承担所有顾客的取货动作。
3. **事件阶段**：随机出现缺货、付款问题、特殊需求等可恢复事件。
4. **结算阶段**：显示收入、成本、满意度、语言表现和常见错误。
5. **成长阶段**：用资金购买普通扩容与装饰；资金和对应英语任务均满足时购买高级服务或自动化；选择下一营业日目标。

### 7.4 经营系统

V1 只保留能支持核心循环的四项指标：

- **现金**：来自订单，支付进货、装修、员工和设备；
- **库存**：决定商品是否可售，并产生补货语言任务；
- **店铺评价**：受服务准确度、等待时间和环境影响；
- **游戏内技能进度**：按具体技能估计，决定学习支架与自动化资格，但不等同于外部学习效果。

经营失败采用轻度后果：

- 所有完成的交易都获得维持经营的基础收入；首次独立正确可获得奖励收入，错误或提示后完成只减少奖励与满意度；
- 当日表现差只影响当天利润和评价；
- 不设置永久破产；
- 必要时提供“轻松营业日”，让玩家恢复库存和评价；
- 复习任务不消耗经营资源；玩家可以重做关键学习任务，但重复试错不能刷独立成功或大量金币。

#### 实体货物与交易一致性

| 状态 | 归属与合法变化 | 必须保持的约束 |
| --- | --- | --- |
| 箱内 | 商品属于指定货箱；玩家可搬动整个货箱 | 抱箱只改变容器位置/持有者，不复制箱内库存 |
| 玩家手持单品 | 从货箱或货架移入手持位，可近看、放回或上架 | 近看仅改变展示状态，不凭空新增或消耗商品 |
| 货架 | 商品属于指定货架槽位，供顾客选购 | 顾客预占与真正拿走分开；可售数量不能包含已预占部分 |
| 顾客购物篮 | 拿取成功后从货架转入指定顾客持有 | 两名顾客不能拿到同一件剩余商品 |
| 结账台 | 篮内商品移至待扫描/已扫描清单，等待付款 | 扫码不增加现金、不再次扣货架库存；重复扫码不能重复计价 |
| 已售出 | 付款成功后以唯一交易 ID 一次性提交收入与已售数量 | 连点、回调重复或刷新不得重复收钱；付款失败保持未售出 |

所有转移由领域命令原子校验并更新，动画只表现结果。完整保存点必须包含容器、货架、顾客和交易的同一版本；不能只存现金、不存相应货物去向。取消拿取应回到来源或合法放置点；顾客放弃购物时，其商品退回有空位的原货架，否则进入可恢复的后仓。缺货、队列满或付款失败不得静默删除商品。

### 7.5 成长分层与自动化的耦合

以下升级规则已由用户确认：

| 类型 | 例子 | 购买/解锁规则 |
| --- | --- | --- |
| 普通经营升级 | 普通货架、存货容量、基础店面扩容、纯装饰 | 只以资金作为成长门槛，不检查英语技能；仍须满足合法摆放和未重复购买等业务约束 |
| 高级服务与自动化 | 自动收银、后续员工补货或高级服务岗位 | 资金足够，且完成该能力明确列出的对应英语任务，二者缺一不可 |

两类升级使用明确的类型字段与独立判定；界面列出价格、作用和适用条件。不得用一个通用“现金 + 三项技能”函数拦截所有货架和扩容。普通成长可以持续奖励经营投入，英语继续影响服务表现与高级能力，不以答错一个词阻断普通扩店。

高级服务与自动化需要同时满足：

1. 有足够经营资金购买设施或雇员；
2. 玩家完成与该能力相关的前置英语任务并达到约定的任务证据，具备培训、检查或接管资格；具体配置遵守 6.6，不以无关任务凑总分。

| 自动化系统 | 被自动处理的重复任务 | 解锁前所需英语 | 解锁后新增英语任务 |
| --- | --- | --- | --- |
| 自动收银 | 普通扫码与付款 | 商品、数量、价格、付款、收据 | 扫码失败、付款失败、收据、是否要袋子 |
| 员工补货 | 常规搬运和上架 | 商品类别、数量、货架位置 | 读送货单、缺货、替代品、纠正上错货架 |
| 普通顾客接待 | 熟悉顾客的标准询问 | 问候、指路、简单推荐 | 培训员工、特殊需求、误会和指出简单问题 |
| 配送 | 标准订单拣货和送达 | 地址、时间、数量、商品确认 | 电话确认、地址异常、漏货、替换商品 |

旧知识仍通过以下方式回流：

- 店铺抽查和员工求助；
- 特殊订单或神秘顾客；
- 玩家主动选择“亲自值班”；
- 新店开业后以新商品重新应用旧意图。

#### 自动化任务合同

自动化必须既像奖励，又保留稳定的英语调用，不能依赖低概率随机故障维持学习：

- 启用后，例行非语言操作量相对手动阶段至少减少 30%；
- 普通模式每个自动化营业日安排 2–4 次主动英语调用，其中至少一次复现旧技能变式，至少一次属于培训、检查或简单异常；
- 异常替代普通顾客任务，不额外拉长营业日；
- 提示后完成可以恢复交易，但不记为独立成功；
- 研究模式保持自动化前后的被评估语言机会数量一致，只改变任务类型和非语言工作量；
- P0 只以自动收银验证本合同；员工补货、普通接待和配送按相同规则在 P1/P2 扩展。

### 7.6 角色成长

| 阶段 | 玩家身份 | 主要行动 | 语言难度变化 |
| --- | --- | --- | --- |
| 1 | 店员兼店主 | 补货、找商品、收银 | 单词、数字、基础交易 |
| 2 | 值班主管 | 分配工作、帮助员工 | 指令、位置、确认、纠错 |
| 3 | 商超经理 | 管理设备、异常与配送 | 信息项增加、同义改写、简单问题与替代 |
| 4 | 商业街经营者 | 开新店、培训团队、处理关键顾客 | 长期版本中的跨场景迁移和 B1 管理沟通 |

### 7.7 装修与摆放

- 商品上架与家具装修分开处理。商品陈列的初始实现建议是“选择合法货架层/槽位后自动对齐”，在小样中验证手感；不把自由堆叠物理作为首版条件。
- 货箱先限制在可识别的安全卸货区或工作位放下，避免堵住顾客通路；若后续允许任意放置，必须同时实现障碍更新和可达性校验。
- 长期目标允许玩家在装修模式中自由摆放货架、收银台、桌椅、装饰和功能设备；
- 摆放使用地面网格，普通营业时不显示网格；
- 家具可拖动、旋转、收回仓库；
- 系统标记入口堵塞、收银不可达、通道过窄等无效布局；
- 店铺功能升级与纯装饰分开定价，避免玩家必须牺牲喜欢的风格换效率；
- 研究版 P0 先提供一套温馨英式风格和固定可用插槽，允许在插槽内拖放与旋转；
- 自由网格摆放、全店可达性校验和第二套现代自然商超风格属于 P1 答辩展示增强项。

### 7.8 开场约五分钟的操作分镜（节奏待验证）

分镜描述玩家控制中的操作状态，不是自动播放过场。步骤按动作完成推进；允许观察、停留、放回、取消和重试，不以时间到达强行切镜或让教学失败。

| 节拍 | 玩家看见与操作 | 教学与反馈 |
| --- | --- | --- |
| 01 看懂小店 | 站在入口，看到收银台、面包架、冰箱、空货箱及 £12 本金 | 一次只提示当前目标；可见“进货 / 营业 / 扩容”入口 |

| 03 拿箱子 | 对准到货后的货箱拿起，箱子位于视野下方；能正常看路并走到卸货点 | 教移动、互动与放下；目标仍为 60 秒内完成首次有效操作，实际时长待试玩验证 |

## 8. 视觉、视角与交互

### 8.1 视觉方向

- 真实比例、容易辨认的形状和材质、适度写实的第一人称 3D；
- 镜头位于成年人视线高度；角色、家具、货箱和商品尺寸一致，不使用儿童化的大头比例或玩具般家具；
- 小店阶段温暖、生活化；商超阶段逐渐现代化、商业化；
- 主色建议：奶油白、鼠尾草绿、深海军蓝、低饱和蓝绿、芥末黄；
- 持续保留木材、绿植、暖光等视觉锚点，使升级后仍属于同一个世界；
- 教学商品须经得起近距离观察：牛奶纸盒的折角/瓶盖、面包的轮廓/外皮/透明包装等应可辨认，不能只用换颜色的方块表示；
- 用光线、对比、空间位置、准星提示和明确动作文字共同引导，不再只依赖微弱发光；独立语言任务不得高亮正确答案；
- 不追求电影级照片质感、复杂物理或与概念图逐像素一致，实际目标以可运行样片中的质量与性能共同确定。

已确认的概念图方向：

- 同一家温暖英国街角小店的三个连续操作画面：抱货箱、近看牛奶、站在收银台后接待顾客；
- 从入口看，收银台在左、面包陈列在右、黑色立式冰箱在后；同款商品在三个画面中保持连续；
- [第一人称分镜与提示词](./art/first-person-storyboard-v1/README.md)作为风格参考；旧伪等距图只保留色彩/材料参考，不再作为镜头和实现目标；
- 大商超仍为后续阶段：明亮、分区清楚并保留温暖元素，尚未完成对应的第一人称 3D 资产验证。

### 8.2 摄像机状态

| 状态 | 镜头与输入 | 退出/恢复要求 |
| --- | --- | --- |
| 空手行走 | 第一人称自由转头与移动，不穿墙 | 可进入任一合法交互状态；不强制镜头对准事件 |
| 抱箱/手持商品 | 保持第一人称，手和物品位于视野下方 | 不遮挡主要通道与目标；可在合法位置放下或放回 |
| 近看商品 | 商品位于阅读距离，支持旋转；暂停角色移动及经营计时 | 退出后恢复原持有者/位置，不能复制或吞掉商品 |
| 上架预览 | 对准可用层位显示摆放预览和数量 | 无效位置给出原因；取消不提交转移 |
| 收银 | 玩家主动到收银侧操作，设备朝向符合双方站位 | 可取消当前操作；未付款物品和金额仍为待结账状态 |
| 装修 | 暂停营业，在合法插槽预览家具 | 确认后更新占用；取消恢复原布局；总览镜头不是首版必需功能 |
| 菜单/管理/暂停 | 释放鼠标，展示可读面板并暂停经营计时 | 明确点击继续后恢复控制；不在文字输入时触发行走 |

主玩法始终以第一人称为准，不沿用旧版全店缩放/平移和固定不旋转镜头。视野角、灵敏度与镜头晃动在小样中校准；默认关闭强烈晃动、运动模糊和强制事件拉镜。打开暂停菜单或页面失焦时，顾客计时和音频同步暂停；近看商品仅暂停经营计时，仍允许主动播放词汇发音。

### 8.3 桌面端基础操作

以下区分 S1 当前操作和完整 P0 约定，不要求用户记住全部快捷键。当前有移动、转头、E 互动、F 近看、G 放下、Tab 切换鼠标、R 重听、B 进货、U 扩容与 Esc 暂停；不支持的装修、自由交谈和键位重设不能由本节推定为已实现。实际键位见 [README](../README.md)。

- WASD 或方向键：移动；鼠标：转头观察；
- E：当前上下文主操作，例如拿起、放下、交谈或操作设备；
- F / 画面中的“查看”按钮：进入商品近看；近看时拖动旋转；
- G：将货箱放到附近可用的安全卸货点，或放回手中单品；鼠标无法锁定时可拖动画面，I/J/K/L 提供备用转头；
- Tab：释放鼠标让页面按钮可点击，或主动申请切回转头；切换本身不主动暂停营业。收银互动自动释放鼠标，不能让玩家必须暂停才能点重听；
- R：重听当前顾客台词；“请再说一遍”播放请求句并慢速重播，文字字幕始终可读；
- B / U：分别打开进货和普通扩容；进货、日结、扩容管理面板会暂停顾客，返回小店后保持鼠标可点击，不自动重新锁定；
- 左键：确认摆放、扫码或操作已激活的界面，不同时触发两个动作；
- 装修时通过可见按钮或提示键旋转家具；不将滚轮强行沿用为全店缩放；
- Esc：取消当前预览/近看或打开暂停，并释放鼠标；页面失焦也须释放控制、清空按住的移动键；
- 菜单、对话和离散动作有可点击入口与清楚文字；移动键支持替代/重设，不依赖 Mac 专用按键；
- 不承诺未经验证的纯鼠标通关或手机触控体验；低游戏经验者的操作辅助单独试玩验证。

鼠标捕获只在玩家明确点击进入游戏后申请；拒绝、不支持或丢失捕获时显示说明，并提供拖动视角或重新进入的可恢复路径。不得让用户困在隐藏鼠标的页面中。[MDN：Pointer Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_Lock_API)

### 8.4 交互可发现性

- 只有距离、视线、遮挡、持有状态和目标状态都合法时才能交互；不能穿墙拿货或远程收款。
- 屏幕同时只显示一个主操作提示；准星指向可操作物时，轮廓/图标与动作文字共同变化，而非要求玩家寻找微弱发光点。
- 引导卡住时逐步补充位置与动作提示；语言辨认提示按 6.10 单独记录，不能把操作便利当作语言答案。
- “拿不起来”“货架已满”“手中有货”“尚未扫码”等状态必须给出短而具体的原因；不让无响应点击成为唯一反馈。

### 8.5 3D 美术资源交付要求

- 概念图用于确定视觉目标，量产资源需另交付模型、材质贴图、碰撞体、交互锚点和必要动画；初始模型交换格式建议使用 glTF/GLB，随技术小样确认。
- 店铺拆为可复用墙地面、货架、冰箱、货箱和收银设备；教学商品优先保证真实尺寸、轮廓与近看细节，背景装饰不得冒充可学习商品。
- 玩家手部至少覆盖抱箱、持物/近看、放置与收银所需表现；顾客至少有行走、停留、拿取与付款表现。具体动作数量、实现方式和资源体积由清单冻结。
- 每种商品的世界模型和近看模型保持同一身份；若使用不同精细度版本，包装、比例与关键辨认特征必须一致。
- 界面提示、词义和字幕由可访问的文本层渲染；包装正文另行排版核对，不直接使用生成图中不可读的细字。
- 助手负责美术方向和制作整合；遇到复杂角色、动作、付费素材或额外工具需要，先说明能力、授权和费用边界，再请求用户决定。
- 模型、贴图、音效、配音、字体和生成素材均记录来源、使用许可及版本；图像生成输出不自动等同于已检查的商用 3D 素材。

## 12. 首发范围与优先级

### 12.0 当前执行顺序

S0 技术小样已有历史基线；本轮先解决其语音、鼠标与升级体验，再完成 S1 首日闭环，最后才扩展到研究版 P0。三层分别验收，S1 流程可运行不能替代后续工程、内容或研究要求。当前 S1 固定两类商品、每日三单和一次普通货位扩容，不等于自动收银、完整买卖双角色或所有 P0 需求已完成。

## 13. 技术方案（S0 基础延续至 S1，完整 P0 继续验证）

### 13.1 技术选型

| 层 | 当前方案与后续目标 | 选择原因 |
| --- | --- | --- |
| 游戏世界 | S0 锁定 Babylon.js 9.23.0 | 已完成相机、材质、模型导入、动画和基础碰撞；扩大内容量前仍需持续性能与跨设备验证 |
| 开发语言 | TypeScript 严格模式 | 尽早暴露类型错误，降低 AI 生成代码的隐性问题 |
| 构建工具 | Vite | 开发反馈快，适合 TypeScript/Web 项目 |
| 界面 | HTML/CSS | 适合对话、菜单、设置、复盘和无障碍文本 |
| 内容与资源 | JSON + Schema 校验；模型格式初选 glTF/GLB | 店铺、商品、顾客、台词、模型与音频引用和核心代码分离 |
| 本地存储 | S1 使用 v4 独立 localStorage 快照；P0 目标为 IndexedDB | 校验、备份、导入/导出、单写入者保护，v3 只读迁移；大规模研究日志不放入同步存储 |
| 语音资源 | 两个真人单词 OGG + 八个预先合成的本地 WAV | 不在运行时调用 TTS 或依赖浏览器英语声线；Piper 仅作离线制作工具，模型和引擎不进网页包 |
| 测试 | 单元测试 + Playwright + 实际浏览器交互检查 | 经营、音频资源和界面生命周期分别验证；多浏览器覆盖与本轮通过项以具体报告为准 |

现有工程依赖 Phaser 4.2.1，但 Phaser 的设计重心是 2D，不作为本次完整 3D 世界的延续方案。[Phaser 官方说明](https://docs.phaser.io/phaser/getting-started/what-is-phaser)

Babylon.js 提供 WebGL/WebGPU、相机、材质、动画、碰撞、glTF 导入和导航等基础能力；S0 使用其中所需的 WebGL 渲染与资产能力，不等于完整 P0 已达到性能指标。[Babylon.js 官方功能说明](https://www.babylonjs.com/specifications/)

S0 阶段已将默认入口切到 `src/sim3d/`；S1 延续 Babylon.js / TypeScript / Vite，不因新增预制音频引入运行时语音服务。旧 Phaser 入口通过 `?legacy=1` 保留。资源体积与许可见[素材来源](./ASSET_SOURCES.md)，本轮运行结果见[S1 首日与验证](./S1_FIRST_DAY.md)，历史检查见[S0 实现与验收](./S0_3D_IMPLEMENTATION.md)。扩大到完整 P0 前继续复核资产预算、持续性能和浏览器兼容性；如更换引擎，须说明原因和迁移影响。

### 13.2 架构原则

```text
HTML/CSS 界面层
        ↕
应用状态与流程控制
   ↙          ↘
3D 场景与交互层   学习/经营规则层
   ↘          ↙
结构化内容与资源（JSON/模型/材质/动画/音频）
        ↕
本地存档（S1 v4 快照；P0 计划 IndexedDB 与假名化事件日志）
        ↓
用户主动导出 JSON/CSV
```

- 游戏渲染、经营规则、学习判定、内容数据和存档分别建模块；
- 应用状态/领域层是现金、货物归属、顾客、交易、学习和进度的唯一事实来源；3D 场景与 DOM 只渲染状态并发送类型化命令，不得各自保存可冲突的业务状态；
- 跨层通信使用有类型的 command/event；随机数由可注入、可设 seed 的服务提供，时间由可替换的 clock 提供；
- 经营数值和学习判定写成不依赖画面的纯函数，便于测试和答辩说明；
- 物品归属、顾客行为、交互模式和付款流程使用显式状态机；扫码、购买、货物转移等命令须幂等，不能依赖动画回调次数结算；
- 顾客行为覆盖进入、浏览、寻找商品、拿取、询问、排队、付款与离店；缺货、占位冲突、队列满和路径失败都有等待、改路、退货或退出策略；
- 家具、货箱合法位置与导航使用一致的占用信息；固定安全布局也要校验合法变化，不能同时承诺任意放置与不更新通路；
- 对话由审核后的模板和插槽组成，不让运行时 AI 任意生成正确答案；
- 核心玩法不依赖登录、云端、大模型或持续网络；
- 时间推进使用帧间时间或固定逻辑步长，不把模拟速度绑定到帧率；
- 每个核心模块需要一页简短说明：输入、状态、输出、失败方式和测试。

3D 技术小样必须验证：相机和鼠标控制、玩家碰撞、货物近看与上架、顾客路径与队列、付款提交、取消/失焦/刷新恢复、音频播放，以及携带代表性资产的实际性能。先用满足任务的简单碰撞和导航方案，不默认引入复杂全物理模拟；小样通过后再锁定具体实现。

### 13.3 AI 辅助开发约束

- 每次让 AI 写代码时明确当前框架与精确版本；
- 一次只实现一个小功能，完成后运行测试并提交 Git；
- 不接受无法解释的核心代码；
- 重要公式、状态机和判定必须有测试；
- 所有新增依赖先说明用途，再决定是否加入；
- 建立术语表和架构说明，避免不同 AI 回合使用不同命名；
- 第一周确认学校对生成式 AI 的披露、引用和代码归属要求。

### 13.4 统一完成定义（Definition of Done）

每项功能只有在以下条件全部满足后才可标记完成：

- 锁定 Node 主版本、包管理器、TypeScript、所选 3D 引擎、Vite、Playwright 及 lockfile；
- 全新目录可通过锁文件安装并完成生产构建；
- 类型检查、代码规范检查、单元测试、内容 Schema 校验、生产构建和对应端到端测试通过；
- 无说明的 `any`、`@ts-ignore` 或双重类型断言不得合入；例外需记录原因；
- AI 辅助改动记录“改了什么、为什么、运行了哪些测试、开发者如何人工验证”；
- 新依赖记录用途、许可证、维护状态和不采用替代方案的理由；
- 模型、材质、动画、图片、音频、字体及 AI 生成素材保留来源、授权和生成记录；
- 同一代表性资产必须在实际游戏中通过近看、互动和性能检查，不能仅凭概念图或灰盒截图宣称美术完成。

### 13.5 旧版迁移与运行交付边界

- 可复用的基础包括商品 ID/价格、英语内容结构、判定与交易纯函数、存档仓库和已有测试思路；需按新规则扩展并重新验证，不宣称原样可用。
- 需要重做或明显调整的是 `src/game/` 世界层、第一人称交互、应用流程、顾客购物与物品归属、分层升级判定和 3D 存档结构。
- 旧版 `GameState` 的后仓/货架数量和单个顾客序号不足以表达新流程；新增容器、槽位、顾客持有、扫描/付款以及安全恢复信息，原库存汇总由统一来源派生。
- 保留旧 2D 存档和历史验收记录；先定义版本映射及备份方案。不能兼容的状态应使用明确说明的新存档或独立命名空间，不静默覆盖旧档。
- S1 使用 `english-high-street:sim3d:v4` 及独立备份；v3 主档/备份只作为经校验的迁移源，原键不修改、不删除。迁移保留旧货物、现金、交易、扫描和升级，不发 £12 本金；新存档才从 £12、空箱开始。导入旧 3D JSON 同样先校验，不接受把 2D 存档当作 3D 状态。
- [localhost:4200](http://localhost:4200/) 为本机生产构建预览，代码或资源变化后必须先 `npm run build` 再刷新；4199 为开发服务。不同主机名或端口是不同存档来源，切地址不代表原存档消失。
- MVP 无需登录、运行时大模型或应用后端；资源首次加载仍需正常托管或本地 HTTP 服务。对外试玩使用固定地址、清楚的构建版本和可诊断加载状态。
- S1 核心语音已采用预先准备的本地音频；顾客和搭配为英式合成短句，单词为已署名真人录音。合成资源的文件完整性不等于教师审核或听觉自然度确认，不能据此宣称正式配音质量和跨设备一致性已达标。

## 14. 非功能需求

### 14.1 浏览器与系统兼容性

| 级别 | 系统与浏览器 | 要求 |
| --- | --- | --- |
| 核心支持 | Windows 10/11：Chrome、Edge 当前稳定版 | 全功能与正式验收 |
| 核心支持 | macOS：Chrome、Safari 当前稳定版 | 全功能与正式验收 |
| 扩展支持 | Windows/macOS：Firefox 当前稳定版 | 核心玩法可完成，允许轻微视觉差异 |
| 尽力支持 | Linux：Chrome/Firefox 当前稳定版 | 不作为答辩阻断条件，但不主动使用系统专有能力 |

- 初始 3D 兼容方案以 WebGL 2 为基线，WebGPU 不作为必需条件；具体支持范围随参考设备小样冻结。创建失败时展示硬件加速和更换浏览器的兼容提示，不承诺用 Canvas 2D 回退运行 3D 游戏；
- 不支持 IE、过旧浏览器或禁用所需图形能力的环境；
- 支持政策写“发布时当前稳定版”，但每份验收报告必须记录精确系统、浏览器和设备版本；
- CI 在 Chromium、Firefox、WebKit 上运行列明的 P0 流程；Windows 发布验收还要使用真实 Chrome 与 Edge，macOS 使用真实 Chrome 与 Safari；
- Firefox 的 P0 核心流程必须通过，允许轻微视觉差异；Linux 只做 smoke test；
- WebKit 自动化不能完全替代真实 Safari，人工清单须覆盖 3D 渲染、鼠标捕获/释放、拖动视角回退、音频/倍速、IndexedDB、下载和字体缩放。Playwright 官方支持 Chromium、Firefox、WebKit 及 Chrome/Edge 品牌浏览器。[Playwright 浏览器测试文档](https://playwright.dev/docs/browsers)

WebGL 已被现代浏览器广泛支持，但具体可用性和速度仍取决于 GPU 与硬件加速。[MDN WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API)

### 14.2 分辨率与响应

屏幕物理分辨率、CSS viewport 和 Canvas 内部渲染分辨率必须分开记录。

| 项目 | 初始方案 | 冻结时间 |
| --- | --- | --- |
| 世界与相机 | 真实比例 3D 坐标；视野角与宽高比独立配置，16:9 仅作构图参考 | 3D 技术小样后 |
| 标准桌面布局 | CSS viewport ≥ 1100×620 | 第 1 月真实设备核对后 |
| 紧凑桌面布局 | CSS viewport 960×540 至 1099×619 | 第 2 月纵向切片后 |
| 过小视口 | 低于 960×540 时要求放大窗口或进入全屏 | 第 2 月可用性测试后 |
| 渲染 DPR | 标准画质暂定上限 1.5；低画质为 1；高画质最多 2 | 第 1 月性能小样后 |

- 验收矩阵至少包含普通窗口、全屏、Windows 125% 系统缩放和 Mac DPR 2；
- 紧凑布局允许折叠次要面板，但必须保留移动、订单、提示和暂停；
- 支持 1920×1080 及常见更高分辨率；增加像素主要提升清晰度，不随意改变相机视野角或放大界面；
- V1 以桌面键鼠为首发输入，提供方向键/重设、可点击离散操作和拖动视角回退；不以纯鼠标操作、手柄或手机触控通关作为已验证承诺。

### 14.3 性能目标

性能会因 CPU、GPU、内存、分辨率、浏览器和硬件加速状态不同而变化。3D 技术小样阶段确定一台普通 Windows 笔记本和一台 Mac 作为参考设备，并记录 CPU、GPU、内存、系统、浏览器、CSS viewport、DPR 与画质档。下列数值沿用为初始目标，尚未经 3D 实测，不能引用旧 2D 结果宣称达标。

技术小样先覆盖一店、两种教学商品和一位顾客的完整循环；研究版压力场景暂以最多 4 位活动顾客、1 路语音和完整 UI 为基线，预热 30 秒后连续营业 5 分钟。必须另行冻结可见商品实例数、家具数、模型面数、贴图尺寸/显存预算、灯光/阴影、骨骼动画数量与近看状态，不能用“30 条商品记录”代替真实渲染负载。最终数量随资源清单与 P0 内容冻结，测试场景和采样方式不得在结果不佳时临时更换。

| 指标 | 初始验收目标 |
| --- | --- |
| 标准画质 | 参考设备中位 FPS ≥ 50，1% low ≥ 30 |
| 低画质 | 中位 FPS ≥ 30，且无持续 1 秒以上的主线程卡死 |
| 时间一致性 | 固定随机种子与输入脚本下，30/60 FPS 的现金、库存、订单结果完全一致；金额用整数最小货币单位 |
| 首次/二次加载 | 显示真实进度；资源清单完成后于第 2 月冻结秒数与网络条件 |
| 长时稳定 | 连续运行 6 个营业日后，活动 NPC、定时器和事件监听器数量回到基线，不单调增长 |
| 后台行为 | 标签页隐藏时暂停；恢复后不跳过订单、音频不重叠 |

实现策略包括模块化模型复用、实例化、纹理压缩、分级细节、分批加载、视锥裁剪、阴影预算、对象池和避免每帧创建对象。低画质可降低分辨率、材质/阴影和非关键动画细节，但不减少逻辑顾客、改变交易结果或删减研究英语机会。性能报告必须保留原始采样环境与数据，并记录首次加载体积、用时与失败恢复结果。

### 14.4 可访问性与成年人友好

- 所有英语语音提供字幕；
- 语音可重复、调速，音效、音乐和语音音量可分别控制；
- 字体至少提供 100%、125%、150% 三档；
- 不只用颜色表达成功、失败或稀有度；
- 倒计时可关闭或延长；
- 核心流程不强迫开麦；
- 关键按钮有文字标签和清晰焦点状态；
- 默认不使用强镜头晃动、运动模糊或强制拉镜；提供灵敏度、视野角和减少镜头运动的设置，并记录第一人称操作不适与卡点；
- 暂停、失焦和文字面板均能释放鼠标，返回后不持续误走动；视角捕获不可用时有明确回退；
- 教程随时可以重新打开。
- 预录音频应在首次用户交互后统一解锁；页面隐藏时暂停，恢复后不得重叠；倍速、重播和字幕须在真实 Safari、Chrome 中验收。

### 14.5 隐私与数据

- 普通模式默认只把进度保存在本机；
- 研究模式必须先展示知情同意，并使用假名化参与者代号；代号对应表如存在，应由研究者在游戏之外分开保存；
- 不默认保存姓名、联系方式、自由文本或录音；
- 麦克风权限只在玩家主动启动语音功能时请求；
- 导出前展示包含的数据；
- 数据保留时间、删除方式和论文匿名化规则需经学校伦理要求确认。
- P2 语音只识别有限意图/关键词，不评分发音或口音，不作为升级或研究任务的唯一路径；使用前提示部分浏览器可能把音频交给远端服务，不保存音频，识别文本是否保存需单独同意；
- 语音验收覆盖不支持、拒绝权限、超时、无结果和网络失败，回退到点击/词块后经营奖励与学习机会等价。

### 14.6 稳定性

- 开箱/拿取/上架/顾客拿货等货物转移，以及付款、日结、升级、装修确认和设置修改形成完整安全快照；写入完成后才标记已保存。镜头移动等高频表现不逐帧写库；
- 不把 `beforeunload`/关闭事件当作主要保存机制；`visibilitychange`/`pagehide` 只用于暂停和尽力提交已有待写数据。IndexedDB 异步事务可能在浏览器关闭时被中止，官方文档明确不应把事务绑定到 unload 事件。[MDN：Using IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)
- 每次迁移前保留最后一个已校验快照；迁移或写入失败不得覆盖它；
- 至少支持前一个正式存档 schema 版本，并为升级成功、失败回滚、损坏快照和旧内容 ID 缺失建立测试夹具；
- 2D 到 3D 为显式大版本迁移：旧位置、顾客状态与升级资格不得无校验套用；不兼容时保留旧档并使用隔离的新档流程，须让用户知情；
- 检测隐私模式、容量不足和写入失败并给出导出存档的恢复建议；浏览器存储默认属于 best-effort，可能被用户清理或在存储压力下回收，因此完整导出不可省略。[MDN：Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- 正式研究开始后固定部署 origin，避免更换域名导致浏览器本地数据无法自动迁移；
- 刷新页面后可从最近一个完整安全点恢复，包括货箱余量、货架陈列、顾客持有、扫描/付款状态、唯一交易标识和合法玩家位置；可恢复位置或将手持物放回安全点，不恢复一半交易；
- 连点交互、重复付款回调、关页和写库失败不得产生多份商品或重复收入；未提交的动作从最后有效快照重试；
- 内容数据缺失时显示可理解的错误，不进入无限加载；
- 顾客寻路失败、音频加载失败和 WebGL 上下文丢失均需有恢复或退出路径；
- 核心端到端流程不得出现阻断性错误。

V1 不包含 manifest、service worker、安装提示或“访问一次后可离线运行”的承诺。答辩离线备用方案是经过验证的生产构建文件与本地 HTTP 启动器；不假设直接双击 `index.html` 即可运行。PWA 安装、离线缓存和缓存更新属于 V1.5。[MDN PWA 安装说明](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

### 15.2 产品指标

- 首日流程无需关键口头介入的完成率；“关键介入”指研究者解释任务目标、下一步或人工解除卡死；
- 是否主动开始第二营业日，只表示会话内继续意愿；
- 装修、升级和自动化的使用情况；
- 3–7 天内的无提醒返回、统一提醒后返回和未返回分别记录；
- 首次卡点、退出点和提示使用情况；
- 物品难以辨认、找不到交互点、视角操作困难和第一人称不适的发生位置；
- 大学生与中年探索样本中分别观察到的字体、语速和操作辅助需求，不做小样本年龄显著性比较；
- 是否能区分“普通扩容花钱”和“高级能力还需对应英语任务”，以及是否能感知自动化减少例行操作但增加新语言责任。

### 15.3 学习指标

- 买方与卖方任务分别报告，不互相替代；
- 任务成功定义为在规定时间内，商品、数量和关键限制均正确；
- A/B 平行任务中 T2 近迁移的首次作答正确率作为主要学习表现指标；
- 商品、数量、价格、口味和特殊要求提取正确率；
- 在不泄漏答案的提示条件下，根据英文指认实物及面对新包装/位置的表现；不能仅凭拿起次数或查看时长推断学会；
- 合适表达与词块组织正确率；
- 请求重复、确认和纠错的成功率；
- 前测、后测与 7 天延迟测试差异；
- 提示依赖是否随重复和变式练习下降。

V1 不以口语流利度或发音为主要结果。若论文需要口语结果，应另设不依赖浏览器识别的前后测角色扮演，并由两名不知道测试阶段的评分者使用预先定义量表评分和报告一致性。

### 15.4 技术指标

- 支持矩阵中的端到端通过率；
- 阻断性错误和崩溃会话比例；
- 存档加载与迁移成功率；
- 参考设备帧率、加载时间和内存趋势；
- 不同帧率下模拟结果一致性。

具体成功阈值应在第一轮 10–15 人纵向切片测试后预先登记。当前可先用以下产品决策门槛：

- 迭代后至少 4/5 可用性用户无需关键口头介入完成第一营业日；
- 至少 4/5 用户能够解释普通升级与高级能力的条件差异，以及英语如何影响服务表现，且不能靠连续错误点击获得独立成功；
- 至少 4/5 用户感知自动化使例行操作减少，并能说出一种新的语言责任；
- 主动进入第二营业日与 3–7 日真实回访分开报告；
- 所有 P0 端到端验收用例在核心支持浏览器通过；
- 研究测试题至少覆盖 T2，并能区分原句记忆与新情境近迁移。

以上阈值是待验证的产品决策门槛，不是学习效果结论。证据优先级为：真实回访与完成任务 > 有成本的选择 > 具体过去行为 > 口头兴趣。

## 16. 用户研究与毕业论文验证

### 16.1 研究问题

- **RQ1（可用性/参与）**：目标大学生能否独立完成核心学习经营闭环，其可用性、即时继续和真实回访表现如何？
- **RQ2（近迁移）**：完成规定训练后，大学生在未见过的平行模拟交易任务中的 T2 表现发生何种变化？买方与卖方表现分别如何？
- **RQ3（自动化机制）**：玩家是否感知到自动化减少了例行操作，同时理解并完成新的语言责任？
- **RQ4（探索性适配）**：40–60 岁成年学习者在桌面操作引导、字体、语速、字幕和提示方面有哪些特殊需求？

### 16.2 开题前需求研究

建议招募：

- 8 名非英语专业大学生；
- 6 名 40–60 岁、最近一个月实际学过英语的成年人；
- 2–3 名英语教师。

访谈优先询问真实行为：最近一次学习、最近一次看不懂菜单或商品、当时如何解决、最大障碍、实际设备、真实可接受时长和最近持续玩的游戏。不要先问“你喜不喜欢这个创意”。

招募依据为年龄、非英语专业、学习经历和生活交易困难；独立场景前测用于识别地板/天花板样本。自制校准不能作为正式 CEFR 分级。正式分析记录基线能力、经营游戏经验和操作熟练度。若中年样本主要只在手机学习，V1 只报告其桌面可用性，不宣称已满足其碎片化使用场景。

### 16.3 原型可用性测试

- 第一轮：5–6 名大学生，验证是否理解目标、操作和学习反馈；
- 第二轮：修正后加入 3–4 名成年学习者，观察低游戏经验和辅助需求；
- 重点记录是否能看清并辨认商品、是否找到交互、第一人称操作是否困难或不适、是否误触也能刷奖励、经营是否压过学习、自动化后是否仍愿意使用英语；不把正常经营赚钱本身当作绕过学习的失败。

### 16.4 正式研究与研究模式

稳妥的可行性研究：

- 24–40 名大学生；
- 前测 → 5 次固定研究任务 → 即时后测 → 7 天延迟测试；
- 第 1 次体验手动买卖交易，第 2–3 次达到自动收银条件，第 4 次体验自动化与异常，第 5 次完成未见过的近迁移任务；
- 前测、后测与延迟测项目预先保留，不得在游戏训练中出现；
- 使用 A/B 平行任务、交换施测顺序，并由教师审核难度与答案范围；
- 成年学习者单独作为探索性可用性样本报告。

研究模式使用固定任务序列或完整记录的随机种子，为所有参与者提供相同目标意图、变体数量、最低暴露次数、提示条件和自动化前后被评估语言机会。额外练习、提示、重播和首次作答全部记录；普通模式保留随机性。

若样本、伦理审批和时间允许，可加入“相同英语内容、相同暴露量的普通练习组”。没有对照组时，只报告个体前后变化、效应量和置信区间，不使用“游戏导致提升”或“优于传统学习”的表述；只有随机对照设计才讨论相对学习效果。

### 16.5 内容与测量审核

- 游戏内容至少由一名具有英语教学经验的教师审核；
- 正式前后测和平行卷至少由两名独立审核者检查目标能力、语用自然度、难度与可接受答案范围；
- 开放评分任务预先制定量表，并报告评分者一致性；
- 保留审核人背景、日期、内容版本、发现的问题和修改结论。

### 16.6 伦理与研究边界

- 第一个正式研究阶段只招募成年人，避免未成年人同意流程扩大风险；
- 在采集数据前确认学校伦理审批或备案要求；
- 明确参与自愿、可退出、匿名化和删除机制；
- 不把小游戏完成数据夸大为真实英国交流能力；
- 论文表述以“可用性、可行性和模拟情境近迁移的初步变化”作为稳妥边界；
- 中年组采用目的性招募、任务观察和主题分析，不与大学生做显著性比较，也不宣称年龄造成差异；
- 即使学习指标没有改善，只要研究过程和工程系统符合预定方案，仍可形成有价值的毕业研究结果。

## 18. 毕业版验收标准

学习结果是否改善属于研究发现，不决定软件是否“完成”。V1 验收分为工程、内容和研究就绪三组。

### 18.1 工程验收

1. 游戏加载并开始后，新用户目标为 60 秒内完成第一次受引导有效操作，不要求先接待顾客，并能继续完成首日；
2. 玩家可以第一人称移动、搬箱、近看、上架，完成买方采购和卖方服务；顾客会自主拿货、排队和结账；
3. 错误后可请求重复、获得渐进提示并恢复交易；
4. 当日结算准确展示经营反馈与游戏内技能进度；
5. 玩家可在固定合法插槽中装修；普通货架/容量/基础扩容只检查资金等业务条件，不以英语任务不足阻挡，并能完成一次可见扩建；
6. 高级服务/自动收银同时要求资金与对应英语任务证据，不能用无关技能总数替代；自动收银能处理两类简单异常；
7. 自动化任务合同通过自动化测试和用户观察验证；
8. 原子存档、最后有效快照、多标签限制、完整导入/导出和版本迁移用例通过；
9. 核心流程在 Windows Chrome/Edge、macOS Chrome/Safari 上通过真实设备清单；
10. Chromium、Firefox、WebKit 的 P0 自动化路径通过；
11. 性能达到 14.3 冻结后的参考设备门槛；
12. 项目符合 13.4 完成定义，并有生产部署与本地 HTTP 备用演示；
13. 箱内、手持、货架、顾客持有、待结账和已售出数量一致；缺货、取消、连续点击及重复付款不会丢货、复制货物或重复收钱；
14. 近看、上架、扫码/付款中途刷新可恢复完整安全状态；2D 旧档不被静默覆盖；
15. 鼠标捕获、释放、失焦、输入文字和回退操作均可恢复；无穿墙交互、持续误走动或无法退出的镜头锁定。

### 18.2 内容验收

1. P0 内容达到第 10 章冻结后的规模，并通过 JSON Schema 校验；
2. 每个核心意图至少同时包含买方和卖方任务；
3. 每个对话模板至少有 3 个审核后的措辞变体，组合不会产生矛盾或无解订单；
4. 所有语音有字幕、倍速与重播，缺失音频有可用回退；
5. 每个学习单元包含第 6.9 节要求的元数据与审核状态；
6. 游戏内容至少由一名有英语教学经验的教师审阅并记录版本、日期和修改结论；
7. 前后测和平行卷由两名独立审核者检查，正式研究保留项不会在训练中泄漏；
8. 教学商品具有可辨认的真实比例、形状与材质，世界/近看模型身份一致；正式辨认测试不靠独有高亮或提前显示的中文答案完成；
9. 模型、材质、动作、配音等资源来源和许可有记录，概念图与可运行资产验收分开。

### 18.3 研究就绪验收

1. 知情同意、参与者代号、退出和数据删除流程完整；
2. 固定研究序列保证参与者在第 4 次任务前体验自动收银及异常；
3. 所有关键事件带第 15.1 节要求的内容、角色、暴露和提示字段；
4. 买方、卖方、T1/T2/T3、训练/前测/后测/延迟测可以分开导出；
5. 完整研究彩排从同意、前测、训练、后测到数据导出无缺字段；
6. A/B 平行任务、顺序平衡和分析方案在正式招募前冻结。

### 18.4 两条端到端验收路径

以下为毕业研究版 P0 的目标路径，不是 S1 已通过的列表；本轮较小的真实首日与异常分支见 [S1 验证记录](./S1_FIRST_DAY.md#验证记录)。

**首日路径（从新存档开始）：**

```text
新用户进入游戏
→ 60 秒内完成拿箱/看货等有效操作并选择辅助模式
→ 在首批货物和送货单中接触今日少量词/词块
→ 以买方身份完成采购/到货确认
→ 搬运、近看与上架，顾客自主找货和拿货
→ 一次听错后请求重复并正确指路或确认需求
→ 顾客到收银台，扫码后成功付款
→ 完成日结并获得现金与游戏内技能进度
→ 用资金购买一个普通货架并放入合法插槽，不额外检查英语门槛
→ 退出、刷新并正确恢复
```

**里程碑路径（使用专用验收存档，不改变正式玩家进度）：**

```text
载入自动收银对应任务与资金接近门槛的验收存档
→ 完成该能力要求的无提示变式任务
→ 同时满足资金与对应英语任务条件并解锁自动收银
→ 处理一次支付失败异常
→ 验证例行操作减少且主动语言调用未减少
→ 完成一次 T2 平行任务
→ 导出假名化研究记录与完整存档
```

除顺利路径外，验收必须覆盖以下分支：

| 场景 | 预期 |
| --- | --- |
| 普通升级：资金足够、英语任务未完成 | 满足合法位置等业务条件即可购买；不能出现英语锁 |
| 普通升级：资金不足 | 不扣款、不增加容量，说明资金缺口 |
| 高级能力：仅资金足够 / 仅对应英语任务完成 | 均不解锁，不扣款，分别指出缺少任务或资金 |
| 高级能力：两项都不足 / 两项都满足 | 前者列出缺口，后者只提交一次购买/解锁 |
| 具备很多无关技能，但缺对应任务 | 不把无关技能总数当作高级能力资格 |
| 放箱或家具会堵路、货架已满、顾客同时拿最后一件货 | 拒绝无效变化或提供恢复路径，库存不为负、不复制 |
| 重复扫码、付款失败后重试、重复付款回调 | 只计价和提交收入一次，未付款货物保持可恢复 |
| 近看/上架/顾客拿货/收银中途刷新或失焦 | 恢复完整安全快照，计时不跳跃、鼠标可退出、货款一致 |

## 19. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 四类店铺或完整商超同时深入开发 | 八个月内无法形成稳定研究版 | P0 只承诺便利店双状态 + 自动收银；商超与其他自动化为 P1/P2 |
| 用户需要顾客英语、玩家却只当店员 | 训练内容与真实痛点、测试指标错位 | 每个核心单元同时包含买方采购/探店与卖方营业任务，分别测量 |
| 经营与英语脱节 | 玩家只记颜色/位置，或被频繁答题打断 | 普通经营保留现金成长；在实物辨认、询问、付款与高级能力中调用英语，区分接触与独立完成 |
| 自动化降低练习量或故障过多 | 后期只剩挂机，或自动化失去奖励感 | 执行自动化任务合同：减少非语言操作、固定语言机会、异常替代普通任务 |
| 两类年龄用户差异过大 | UI 和难度无法同时适配 | 共用核心任务，辅助/操作分层；正式研究与探索样本分开 |
| 语音识别跨浏览器不稳定 | 核心流程在部分设备中断 | 语音为 P2；始终保留选择、词块和键入回退 |
| AI 生成代码不可解释 | 调试困难、答辩风险高 | 小步提交、严格类型、纯逻辑测试、模块说明、锁版本 |
| 美术与内容量过大 | 近看模型、人物与动作成本超出预期 | 先验证两种代表性商品和一位顾客；模块化制作，3D 小样后重估 P0，不把概念图当可用资产 |
| 第一人称操作困难或不适 | 玩家无法顺畅移动、找货或持续体验 | 灵敏度/视野角/晕动辅助、清晰交互提示、暂停与恢复；单独观察低游戏经验用户 |
| 实体货物与收银状态不一致 | 刷新、取消或重复点击造成丢货与刷钱 | 统一归属、幂等命令、完整安全快照，覆盖每个转移的失败与恢复分支 |
| 低画质改变任务或研究暴露量 | 不同设备获得不同英语机会，结果不可比 | 降低渲染细节而不删除逻辑顾客、订单或语言任务 |
| 不同电脑性能差异 | 低配设备卡顿或模拟速度异常 | 参考设备、画质档位、固定逻辑时间、性能预算 |
| 浏览器本地存档被清理或写入中断 | 丢失进度或正式研究日志 | 安全点原子写入、有效快照、导入/导出、固定 origin、研究现场及时导出 |
| 研究结论证据不足 | 论文无法支持主张 | 平行任务、延迟测试、假名化日志、教师审核、谨慎表述 |
| 桌面首发不符合中年用户真实设备 | 无法代表其长期采用 | 只声称桌面可用性；访谈记录真实设备；移动端放 V1.5 |
| 开题/伦理/AI 规则未知 | 后期返工 | 第一周向导师或教学办公室确认书面要求 |

## 20. 待落实事项与决策边界

已确认的第一人称方向、实物辨认重点和两类升级规则不重复询问。以下事项按阶段落实；学校/研究协作问题不阻塞最初技术小样，但不得在没有参考设备、资源检查或授权的情况下承诺最终性能、正式研究就绪或第三方支出。

1. 学校准确的开题、伦理审批、中期检查和最终提交日期；
2. 毕业项目更看重技术实现、游戏设计还是学习效果研究；
3. 学校关于生成式 AI 辅助代码、图片、音频和论文披露的规定；
4. 主试玩设备已确认：14 英寸 MacBook Pro、Apple M5 Pro、48 GB 内存、键盘与外接鼠标；后续补普通 Windows 参考机和真实浏览器矩阵，不重复询问已确认信息；
5. 能长期协助审核内容的英语教师及其审核时间；
6. 第一座英国城市的具体叙事背景，或是否使用虚构城市；
7. 正式产品名是否继续使用《英语商业街 / English High Street》；
8. milk / bread 保留已署名的英式真人录音；S1 八条搭配/顾客短句使用已记录开放来源的本地 Cori 合成语音。用户需试听确认自然度，正式配音、扩展台词及教师审核仍待后续落实；
9. 研究样本量和是否设置对照组；
10. 答辩是否要求公网部署，还是本地演示即可；
11. 3D 建模、模型转换与动画工具的可用性；若需要安装、付费模型/动作或配音服务，提前说明用途、授权和替代方案并取得相应许可；
12. Babylon.js 9.23.0、默认键位、安全卸货点和商品自动对齐已在 S0 实现并完成核心路径检查；用户仍需确认手感和视觉质量，完整跨设备与性能结论继续验证；
13. 高级能力对应的英语任务清单、资格阈值与经济参数；普通升级不得借此重新增加英语门槛。

## 21. 决策记录

| 决策 | 当前结论 | 原因 |
| --- | --- | --- |
| 首发平台 | 桌面浏览器 | 先保证完整体验与跨系统可访问，再做手机 |

### 23.2 S0：可玩 3D 技术小样（历史基线）

范围：一间店、牛奶和面包两种教学商品、一位顾客；允许用测试货箱开始，先不扩充全部采购、经营日与研究内容。

```text
进入小店 → 自由走动/观察 → 拿箱并放下
→ 近看商品与听发音 → 上架
→ 顾客自主购物 → 扫码与刷卡收款
→ 保存 → 刷新继续
```

S0 当时只提供简短付款提示；用户试玩暴露的自动开口、鼠标与升级入口缺口由 S1 接续处理。下表保留 S0 的原验收目标，历史检查以 S0 验收记录为准，不能移作 S1 的通过证据。

| 检查项 | 通过条件 |
| --- | --- |
| 画面与实物 | 用实际 3D 模型展示已确认的材料氛围；牛奶和面包近看可辨认，不用换色方块冒充最终商品 |
| 操作 | 能走、看、搬、放、近看、上架、收银；提示明确，取消/失焦可恢复，不穿墙或困住鼠标 |
| 顾客 | 能自主找到货架、拿货、到收银台与离开，路径失败不永久卡死 |
| 货款 | 数量守恒；重复扫码/付款不刷钱，失败不提前售出 |
| 存档 | 中途退出/刷新恢复完整安全点；旧 2D 存档保留 |
| 性能 | 记录实际设备、代表性资产、帧率、加载和音频结果，据此决定是否锁定引擎与扩大规模 |
